## 1. 要解决的真实问题和目标

当前 PR bot 已有全量审查、修复验证、终审、误报核验和自动收尾等能力，但长期通过局部补丁扩展，使审查阶段、问题核验、Review Thread、普通 PR 评论、隐藏 Session 记录和异常恢复之间形成复杂的特殊逻辑。

用户可能遇到：评论存在但未被处理，旧问题在 Bot 升级后无法恢复，已解决问题重复提出，Thread 与审查结论不一致，或者必须遵循复杂格式才能提交异议。这增加日常操作和代码维护成本，也可能造成错误 READY。

本任务以**一条标准审查工作流**为中心收敛逻辑，目标是：

- 正常审查路径简单、可预测，不再按功能堆叠不同流程。
- GitHub PR 保存所有持久化审查事实；一个问题具有唯一、可恢复的处理结论。
- 修复与 dismiss 进入同一问题核验及结案流程。
- 新版 Bot 可以仅根据 PR 中可信的正式记录恢复审查上下文。
- 用户只看到简洁、直接的结论和下一步；机器证据完整、可折叠。
- 复用现有执行能力与安全保护，避免以删除代码或减少文件数代替真正统一。

## 2. 使用者、失败代价

**使用者**：PR 作者、仓库维护者、本地 Coding Worker、PR bot 及未来自动化消费者。

**失败代价**：

- 遗漏未解决问题、错误关闭或错误 READY。
- 旧评论、已批准的 dismiss 或已经 FIXED 的问题没有被后续审查正确继承。
- 用户反复发命令、转述证据、手动恢复上下文。
- 重复模型调用浪费预算；提交变更与审查结果错配。
- 每修复一个例外又产生一条互相冲突的处理规则。

## 3. 标准审查工作流

### 3.1 首轮全量审查

PR 进入可审查状态，或用户手动要求审查后，针对当前 PR 的完整改动执行独立检查：

- **全量覆盖且无阻塞问题**：直接 READY。
- **发现问题**：每个问题建立稳定、正式、可追溯的问题记录，进入修复流程。
- **未完整覆盖、检查失败、证据无法确认**：不得 READY，保留准确的未完成状态。

### 3.2 Worker 修复、用户请求验证

Worker 修复并 commit/push 后，由用户手动发送日常复审命令 **@gemini review**。普通 push 不自动触发付费复审。

Bot 读取最新 HEAD、完整未解决问题记录、各问题的 Thread 回复、适用的用户异议和核验证据，集中验证：

- **FIXED**：证实代码修复有效，记录证据并自动 Resolve 对应 Thread。
- **DISMISSED**：用户理由经独立核验成立，记录结论并自动 Resolve。
- **OPEN / STILL OPEN**：问题仍存在，在原问题 Thread 回复明确原因，保持阻塞。
- **UNCERTAIN**：证据不足，保持阻塞并说明缺少什么。

同次验证还必须检查**本次新提交的全部代码差异及其相关影响**，识别新引入的回归和独立缺陷；新问题进入同一问题生命周期。遗漏检查、无法确定、回归问题未处理时不得 READY。

全部阻塞问题核验结案后，**自动衔接全量终审**；否则继续由 Worker 处理，由用户手动请求下一次验证。

### 3.3 第二轮全量审查（终审）及收尾

终审再次完整检查整个 PR：

- 完整检查无阻塞问题：READY。
- 发现问题：创建正式问题记录，进入修复与验证。
- 终审发现的问题核实解决，且最新修改及其相关影响已经完整、充分地验证，没有新阻塞问题：**直接 READY，不机械执行第三轮全量审查**。

若终审之后的新提交改变关键共享边界、核心结构或之前审查证据所依赖的基础，导致先前审查结论不能充分覆盖最新 HEAD，必须扩大审查范围，必要时再做全量审查；不能以“最多两次全量”为理由省略必要验证。

### 3.4 正常触发及阶段推进

- 日常由用户手动发起修复验证；重复请求不得重复消费已完成、仍有效的审查。
- 阶段达到条件时自动继续，不需要用户手动选择 full、verification、audit 或 closing。
- 模型选择、异常恢复及人工风险接受可以保留独立操作，但不成为额外的日常工作流。
- 自动运行受资源、安全及停止条件约束；不得无条件无限循环。
- 审查结果必须严格对应它实际检查的提交，旧 HEAD 的 READY 不得沿用到新 HEAD。

## 4. GitHub PR 是唯一持久化审查事实来源

### 4.0 产品原则：事实落笔，一段一结，下一段只读交接

- **真相在评论区，工作基于评论和 Thread。** 任何审查事实（问题、结论、证据、覆盖范围、费用、状态变化）都必须写成人可直接阅读的 PR 评论或 Thread 内容，并有来源（谁、在哪个提交、依据什么）。不存在只有 Bot 能读、人看不到或无法读懂的审查事实；用户任何时候都不需要借助 Bot 的记忆理解或接手。
- **每一段审查都有明确、可验收的结束标志。** 首轮审查、修复验证、终审、收尾各为一段；一段结束时必须写下完整的交接记录（实际审查的提交、覆盖范围、每个问题当前结论、未完成事项、下一步由谁做什么）。没有写下该记录，这一段不算结束，下一段不得开始。
- **上一段不得隐性影响下一段。** 下一段只依据已写下的交接记录和代码本身工作；记录缺失、不完整或相互矛盾时，明确停止并说明缺什么，而不是沿用未记录的假设继续。
- 清除 Bot 的全部运行缓存后，仅凭 PR 页面上的记录必须能复现当前所有问题、结论、进度和下一步。

### 4.1 问题记录以 GitHub Thread 为主

发现问题时，尽可能在代码行上发布一条可独立理解的 Review Thread；无法锚定时，用拥有同等稳定身份、可读性与追溯能力的正式 PR 问题记录，不可丢弃问题。

每个问题记录必须具有：

- 稳定 ID、等级（如 P2/P3）、标题、具体失败条件及代码位置。
- 首次发现时的提交、适用的代码范围。
- 后续相关修复提交、核验尝试、用户或 Worker 的回复及引用证据。
- 每次验证的理由、结论和对应 HEAD。
- 当前问题结论、修复处理状态、修复累计次数及必要历史。
- 与实际 GitHub Thread / 评论的稳定关联。

**问题的正式核验结论是权威**；GitHub Resolve 是结论的同步表现，用户手动 Resolve 不等于已经核实。Thread 中的用户主张也不因被写下来就成为已核实事实。

### 4.2 审查批次写在 GitHub PR 正式报告

每轮全量审查或修复验证留存一份可读取的正式审查记录，包含：

- 审查类型、目标 HEAD、实际审查范围和覆盖是否完整。
- 本轮发现的新问题、原问题的处理结果、遗漏或未核实事项。
- 适用的执行/运行身份、费用与必要验证证据。
- 是否满足后续阶段或 READY 的条件，以及真实下一步。

即使一轮没有发现问题，也需要能独立证明其覆盖和完成情况。

### 4.3 唯一权威与恢复

- 每个问题只存在一套可信的正式结论，不再以与 Thread 分离的隐藏 Session 问题账本作为第二权威；也不允许把事实以编码、压缩或其他人无法直接阅读的形式存放（包括对人不可见的数据块）。
- Bot 运行时从 GitHub PR 的正式、可信、完整记录重建审查上下文；人和新版 Bot 都能从这些记录理解已发生的事实。
- 允许执行期间使用缓存、锁、临时计算状态；这些不能成为唯一的持久化审查事实。
- 版本升级、评论替换、Thread 状态变化和运行中断，不能静默丢失未解决问题、已核实结论或必要审查证据。
- 如果记录缺失、损坏、不可兼容、权限不足或无法完整读取，必须安全停止，不得默认为无问题。
- 本需求不预先指定底层存储实现或如何处理 GitHub API 限制，Design 阶段必须验证可行性。

## 5. 问题的两个正交状态维度

### 5.1 问题结论

- **OPEN**：问题仍未结案。
- **FIXED**：代码修复已经证实有效。
- **DISMISSED**：误报异议经过独立核验成立。
- **UNCERTAIN**：无法得出可靠结论，继续阻塞。

结案问题及其核验理由在后续审查中继续有效。不能仅因标题、表述或审查轮次变化而重复产生同一问题；如果新代码提供了足以推翻之前结论的新证据，仍必须允许重新报告。

### 5.2 修复处理状态

- **NORMAL**：正常修复过程。
- **REPEATED_REWORK**：一个问题进入第三次及以上的独立代码修复尝试。

要求：

- **每个问题独立计数**，保留每次修复尝试所对应的 commit 范围、核验结论和理由。
- 第三次独立修复尝试起首次进入 REPEATED_REWORK，并形成**可持久化、可供未来自动化消费、幂等的状态转换事件**。
- 第四、第五次及以后继续累计，但相同尝试的重复审查不能重复计数或重复触发首次转换。
- Dismiss 异议核验不计入代码修复次数。
- 问题最终 FIXED / DISMISSED 后仍保留累计次数和历史过程。
- REPEATED_REWORK 本身**不阻断正常继续修复**，不是 PR 全局的 HUMAN_REQUIRED。
- 本任务仅建立未来自动化可消费的状态与转换证据，**不实现**新的自动修复或根因分析 Agent。

普通修复验证**取消固定两轮上限**，也**不设绝对的轮数或次数上限**：数字上限触发后没有可行的下一步，只会变成形式。重复修复的信号是 REPEATED_REWORK 这一状态变化本身；它被持久记录后，由未来自动化中的人工暂停点消费，使人可以在此介入。本任务不建立该暂停点，只保证状态变化可靠、可读、可被消费。资源不足或安全条件不满足时仍必须明确停止，并按 §8 记录。

## 6. 自然语言评论与异议处理

- 用户可在问题 Thread 中用自然语言说明误报异议、设计依据、路径、链接、测试及修复证据。
- 不强制固定的 Reason/Evidence 字段、最少字数或固定的证据条数；仅保留必要的操作意图识别、权限、安全与合理长度限制。
- Bot 应读取完整、有权限的相关评论，将主张与已核验事实区分，验证理由与最新代码；信息不足则在对应问题处请求补充，而不是仅因为排版不符合机器格式就拒绝。
- 尚未处理的明确请求，或经过编辑的相关说明，应有可预测的处理机制；已完成请求不得因重复读取而重复执行。
- 不得盲目把历史普通聊天评论当作自动化命令；需要明确意图、可信来源、适用对象与幂等保证。

## 7. 面向人和 AI 的双层展示

GitHub PR Review 报告和问题记录按照同一规则展示：

- **默认展开（人看）**：本轮结论、需要处理的问题、当前是否可继续，以及下一步由谁做什么。内容简单直接。
- **默认折叠（AI 恢复与人工复核）**：提交、审查范围、覆盖证据、模型和运行记录、费用、核验过程、历史与引用。

折叠只是阅读呈现，不意味着隐藏、秘密或第二权威。折叠详情必须是人可直接阅读的明文，可读取、可恢复，且不得包含凭据或其他不应公开的信息。人类摘要和机器详情必须来自同一份事实。

## 8. 必须保留的正确性、异常和安全边界

- READY 只适用于最新有效 HEAD，且全部必要审查范围与问题核验已完成。
- 所有未解决、未覆盖、不可验证及证据不确定的阻塞事项持续阻止 READY。
- 结果按实际检查过的 commit 记录，不可混用旧提交的结论。
- 终审之后的修复必须经过差异及相关回归检查；重大变更需升级审查范围。
- 同 PR 的并发任务必须序列化或有等价防护；记录读写需避免丢失更新与重复结论。
- 运行中断、重复事件、重复命令、记录恢复须幂等；不能重复计算同一尝试或无依据重复扣费。
- 模型失败、超时、部分覆盖或预算不足时不可伪造 PASS。预算（费用）保护的作用是防止无人看管时持续花费，不是质量结论：触发时写下“因费用暂停，等待人决定是否继续”，并记录已花费用和停在哪一步，不得表现为审查失败或通过。
- 人工风险接受与独立审查结论分开标记，不因人工决定而假称无 Bug。
- 保留必要的认证、权限检查、可信来源校验、模型隔离、预算限制和 fail-closed 行为。
- 遇 HUMAN_REQUIRED 必须停止，不通过新任务、reset 或改写结论绕过已有强制关卡。
- 已运行的旧 PR 不需在本任务里全部迁移；新逻辑不能静默抹除旧审查事实，不能恢复时要明确阻塞。

## 9. 明确不做什么

- 不重新设计整套状态界面或 UI。
- 不重新建设已有 ReviewLoop 的 Plan/Design/Code 工程审查机制。
- 不以文件数、代码行数减少为验收目标。
- 不在本任务额外开发新的 AI 审查模型、分片引擎或预算引擎。
- 不增加与已有机制重复的审查关卡。
- 不让 PR bot 自动改写业务代码、自动合并 PR 或扩大授权。
- 不批量迁移所有历史 PR，也不删除正式历史审查证据。
- 不实现未来的自动化修复或根因分析 Worker。

## 10. 可观察验收标准

1. 首轮全量审查覆盖完整、无阻塞问题，可以直接 READY。
2. 多条问题经过一次 Worker 修复提交后，Bot 能统一读取并逐条核验。
3. Bot 对已证实 FIXED / DISMISSED 的问题写下结论并正确 Resolve；仍未解决的在原问题记录中解释并保留阻塞。
4. 用户可以在 Thread 用自然语言提出 dismiss；核验准确且不因无关格式拒绝。
5. 任何修复提交产生新的回归问题时能被审查发现并阻止 READY；未审完时不能放行。
6. 首轮问题全部结案后自动进行一次完整终审。
7. 终审发现的问题修复且回归验证充分后可直接 READY；影响原有审查有效性的新提交会扩大审查范围。
8. 已结案问题及其设计/代码核验依据可在后续轮次复用，既不无故重复报告，也不掩盖真正复发。
9. 在运行时缓存丢失或 Bot 版本更新后，能够从 GitHub PR 的正式记录恢复问题、核验结果、审查覆盖与进度；无法恢复时安全停止。
10. 每个问题的独立修复次数准确；第三次产生一次 REPEATED_REWORK 转换事件；继续修复不会被固定轮数限制；结束后历史仍可查。
11. 人看到展开的简洁摘要，AI 能读取默认折叠的完整证据，二者不出现互相矛盾的结论。
12. 重复命令、并发触发、强制推送/历史改写、审查中断、评论修改、记录缺失及模型/预算异常都不会产生错误 READY 或重复结论。
13. 原有必要权限、安全、预算、审查真实性保护得到回归验证，非授权行为不发生。
14. 每一段审查结束时，PR 上都有一份人可直接阅读的交接记录和明确的结束标志；缺少该记录时下一段不会开始。
15. 清除 Bot 全部运行缓存后，仅凭 PR 页面记录可恢复所有问题、结论、进度和下一步；PR 中不存在对人不可读的审查事实。
16. 实际 PR 端到端验收包含：首审通过、多问题修复、部分修复、自然语言 dismiss、修复回归、终审、收尾、第三次修复状态转换、恢复和失败阻塞。

上述为预期验收义务，**未实施或未运行时不得写成 PASS**。

## 11. 已确认决定、仍待 Design 核实的事项

### 已确认的产品决定

- 一条由“全量审查 → 问题核验 → 全量终审 → 必要收尾核验”组成的标准路径；首审无问题直接 READY。
- 普通 push 不自动发起付费复审，用户用单一日常 review 入口手动继续；必要阶段可以自动衔接。
- GitHub PR 是唯一持久化审查事实来源。问题以 Thread 为主、审查批次有正式报告；不建立重复问题权威。
- FIXED 与 DISMISSED 通过统一核验和结案机制处理。
- 普通修复不设固定两轮次数上限；每个问题的第三次修复尝试起进入可供未来自动化消费的 REPEATED_REWORK。
- 人类摘要默认展开、AI 详细证据默认折叠；暂时不重做状态界面。
- 不因整理架构而弱化正确性、安全或已存在的强制审查门槛。
- 产品原则：真相在评论区，工作基于评论与 Thread；每段审查有可验收的落笔结束标志和完整交接，下一段只读交接；不存在只有 Bot 能读的事实。
- 不设绝对的轮数或次数上限；重复修复以 REPEATED_REWORK 状态变化为信号，由未来的人工暂停点消费；费用预算触发时记录并暂停等人。

### 需要 Design 核实的技术事实

- GitHub API 如何可靠读取、稳定关联和写入 Thread、Review 及普通评论；被编辑、分页、容量限制和无法锚定的情况如何处理。
- 如何在“GitHub 是唯一审查权威”的前提下保留强一致并发、幂等、审查恢复与准确预算记录。
- 现有模型执行、分片、校验器、安全能力哪些能直接复用，以及哪些重复判断应当合并。
- 新旧审查记录兼容、无法恢复时的停止规则和必要最小过渡方案。
- 修复增量如何判定审查覆盖充分，以及哪些修改使终审证据失效。
- REPEATED_REWORK 的稳定事件身份与未来自动化消费边界。

以上是设计研究问题，不授权 Design 更改 Plan 的需求或验收条件。Design 需比较 Options、明确 Assumptions，末尾交付 Work Contract，并独立审查。
