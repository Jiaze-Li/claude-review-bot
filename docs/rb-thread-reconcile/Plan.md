Plan — RB-THREAD-RECONCILE-01：每轮审查都对账机器人自己发在评论区的问题，旧问题不再被遗漏

状态：Plan v1.0（等待用户说 Design）
任务仓库：Jiaze-Li/review-bot，基线 main = 9f8e2b7
policy_sha：7f01e5a3ff53ed13ba763d684a098c0989425ec4

====================================================================
1. 背景与现场（已核实）
====================================================================
- 现场：SpinLab PR #195。评论区共 7 条机器人发的问题线程：
  · 最新一条 P2 已被机器人确认修复并自动关闭；
  · 本轮新审出 2 条 P3，仍开着（正常）；
  · 另有 4 条 11 月 10 日的旧线程（3 条 P2、1 条 P3）一直没关，GitHub 标记为"代码已变动"，
    但机器人每轮运行的日志都只写"0 条线程被关闭"。
- 原因（已查日志与代码）：机器人只处理"当前会话里有记录"的问题。这 4 条属于更早一轮会话，
  那一轮会话后来被重置，当前会话里没有它们的记录，所以机器人既不关它们，也不再检查它们是否真的修好。
- 后果：用户在 GitHub 上看到的"未解决问题"和机器人认为的"未解决问题"对不上；
  旧问题可能已修好却一直开着，也可能没修好却无人再查。
- 这是机器人原有的行为，不是 PR #89 引入的。

====================================================================
2. 目标
====================================================================
G1. 以评论区为准：每轮审查开始时，不只看本轮会话，还要对账 PR 上机器人自己发的问题线程。
G2. 会话里查不到记录的旧线程，当作"待核实的旧问题"：核实后修好了才关，没修好继续算未解决并重新记入。
G3. 用户在 GitHub 上看到的未解决线程，与机器人认为的未解决问题保持一致。

====================================================================
3. 非目标
====================================================================
- 只对账机器人自己发的线程；用户和其他人手写的评论一律不碰（用户已确认）。
- 不放松"必须核实才算修好"：人手动点 resolve、或线程显示"代码已变动"，本身都不算修好。
- 不改 READY 与问题关闭的权威规则、严重级别含义、预算与费用上限、模型选择、分片上限、验证轮数、接力次数。
- 不新增"第二套"问题记录或平行的真相来源；评论区线程作为输入，会话仍是严重级别、预算、轮数的记录处。
- 不改 PR #89、#86 已合并的逻辑；不改 SpinLab。

====================================================================
4. 约束
====================================================================
- 线程由机器人发出时已带隐藏标记，识别"是不是机器人发的"必须依赖作者身份加标记，不靠文字猜。
- 核实旧问题需要读当前代码并判断，可能花钱；必须在现有预算和上限内，并设单轮处理条数上限。
- 不得新增会话写入者、不得新增会话字段，除非 Design 证明必要并回到用户确认（沿用 PR #89 的边界）。
- 线程很多（数十条以上）时要有明确的上限与"还剩多少没处理"的如实提示，不能静默丢弃。

====================================================================
5. 可观察的验收标准
====================================================================
AC1  现场复现：会话里没有记录、但机器人自己发的旧线程，在下一轮审查中被识别出来，
     评论里如实说明"发现 N 条旧线程，已核实 X 条已修好并关闭、Y 条仍存在"。
AC2  已修好的旧线程被自动关闭；没修好的不关，并作为未解决问题重新计入（会阻挡合并的级别照常阻挡）。
AC3  用户手动 resolve 的旧线程，如果核实发现问题仍在，会被重新打开并说明原因（与现有对已知问题的做法一致）。
AC4  用户和其他人手写的线程不被读取、不被关闭、不被回复。
AC5  无旧线程需要处理时，评论、状态、花费与改动前逐项一致（回归）。
AC6  超过单轮处理上限时，评论明说"还有 N 条没处理，下一轮继续"，不静默丢弃，也不超预算。
AC7  READY、REWORK、HUMAN_REQUIRED、PARTIAL、AUDIT_PENDING 等既有状态的判定与改动前一致。
AC8  所有既有自动化测试通过；新增测试覆盖 AC1–AC6，含正向、负向、旧会话数据与"线程很多"用例。
AC9  真实复测：用 SpinLab #195 的 4 条旧线程验证；该复测花钱，不属于代码阶段，需用户另行授权。

====================================================================
6. 已确认的决定
====================================================================
D1  新任务，走完整流程：Plan → Design → Code，每阶段结束停下等用户明确说下一步。
D2  对账范围只限机器人自己发的线程（用户已确认）。
D3  方向：评论区作为输入、会话继续作为记录处；"每轮对账评论区"是原则（用户已认可）。
D4  是否分两步（先只识别汇报、再放开自动关闭）：Design 评估后给推荐，用户拍板。

7. 未知前提（Design 必须查实，不得假设）
====================================================================
U1  旧线程的"核实"复用现有验证流程是否可行？现有验证输入需要哪些信息，旧线程里是否都有（路径、标题、正文、行号）？
U2  核实判定为"仍存在"时，如何记入会话而不新增字段、不新增写入者？是否复用现有写入点？
U3  旧线程所指代码已被删改、或文件已不存在时，如何判定（视为已修好、需人工，还是无法核实）？
U4  单轮上限取多少合适？与现有预算、分片上限如何配合？
U5  对账放在每轮的哪一步最稳妥，才不增加无谓花费（例如只在验证类、完整审查类运行里做，记账类运行不做）？
U6  改写历史（#86 场景）后旧线程的位置全部失效时，对账如何处理？

8. 范围与风险
====================================================================
预计触及：线程读取与识别、验证输入的组装、验证结果落地（关线程/重新记入）、评论汇报措辞、测试与一页说明。
风险：
- R1 把"没修好"的旧问题误判为修好并关闭（最严重，AC2/AC3 专测）。
- R2 误碰非机器人线程（AC4 专测）。
- R3 旧线程很多时费用失控（AC6 与预算上限专测）。
- R4 核实把本已放弃的老问题全部复活，造成噪音；Design 需给出用户能理解的取舍。
