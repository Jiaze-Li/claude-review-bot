Plan — RB-AUDIT-CONTINUE-01：验证通过后，最终审查不能无声停住，也不能装作还在跑

状态：Plan v1.0（已提交，等待用户说 Design）
任务仓库：Jiaze-Li/review-bot（本地目录 review-bot），基线 main = a815484
policy_sha：7f01e5a3ff53ed13ba763d684a098c0989425ec4

====================================================================
1. 背景与现场（已核实，非推测）
====================================================================
- 现场：SpinLab PR #195，机器人对最新提交的验证已通过（旧 P2 判定已修复），会话状态变成"等待最终审查"（AUDIT_PENDING）。
  之后没有任何新的运行，PR 页面上一直显示"最终审查待定"，看起来像还在跑，实际没人在跑。
- 机器人本该在验证通过后自动接着做最终全面审查（review-bot 的 continue-review 逻辑，代码注释写明
  "every finding is settled and only the final full review is left"）。
- 没有接着跑的原因（已查日志与代码）：
  1) 自动接力的条件之一是"会话里不能有覆盖不完整记录"。195 的会话里留着上一轮旧提交的
     "1 个测试文件没审完"记录；验证这一步不会清掉它，所以接力判定为"没有可接着做的"，直接停止。
     工作流那一步执行成功、没有报错，所以没有任何失败提示。
  2) 停住时，页面评论仍写"最终全面审查会自动运行"；提交状态是黄色"待定"（和"正在运行"同一种颜色）。
     用户因此无法区分"在跑"和"已停"。
- 这两点都是机器人原有的行为，不是 PR #86（改写历史后的审查范围恢复）引入的；#86 只是让这个现场第一次走到这里。

====================================================================
2. 目标
====================================================================
G1. 验证通过、只剩最终全面审查时，机器人自己接着做，不被过期的覆盖记录挡住。
G2. 无论什么原因没能接着做（接力被拒绝、接力启动失败、次数上限），页面必须明确说出：
    "现在没有在运行；要继续请发某某指令"，不得再写"会自动运行"，状态颜色/文字不得让人误以为在跑。
G3. 真正在跑的时候，仍显示"在跑"，不被 G2 误伤。

====================================================================
3. 非目标
====================================================================
- 不改审查结论的权威规则：什么算通过（READY）、什么算问题关闭、问题的状态流转都不变。
- 不改费用与预算上限、模型选择、20 片分片上限、验证轮数上限（2 轮）、接力次数上限（3 次）。
- 不改 PR #86 已合并的"改写历史后恢复审查范围"逻辑。
- 不替用户合并、不替用户发触发评论去花钱；不改 SpinLab。
- 不新增"第二套"审查结果记录；复用现有会话。

====================================================================
4. 约束
====================================================================
- 状态颜色在 GitHub 上只有"待定/成功/失败/错误"几种；"待定"天然像"在跑"。要让用户能区分，
  只能靠状态文字、评论正文，或换成别的状态（是否换由 Design 评估并说明对必需检查的影响）。
- 必须保持"已经通过 READY 的 PR 不被误改状态"；不得因为这个任务让没跑完的审查被显示为通过。
- 接力是尽力而为的步骤（失败不拖垮整个运行），这个性质要保留；但失败不能再是无声的。
- 复测需要真实花钱，任何付费触发都要用户另行授权。

====================================================================
5. 可观察的验收标准（给用户看的结果）
====================================================================
AC1  现场复现：会话停在"等待最终审查"，且带着上一轮旧提交遗留的"没审完"记录时，验证通过后，
     机器人会自己启动最终全面审查，用户不需要再发任何指令。
AC2  过期记录不再显示：覆盖不完整的提示只在它属于当前提交时才出现在评论里；上一轮遗留的不再展示。
AC3  当前提交确实有"没审完"的文件时（真实部分覆盖），行为与改动前一致：仍按既有规则继续或停下，
     并如实列出没审完的文件，不被 AC1 的修复掩盖。
AC4  接力没有启动时（上限已到、启动失败、其它原因），评论里明确写出"当前没有在运行"、原因，
     以及用户该发的一句话；不再出现"会自动运行"。
AC5  真正在运行时，评论和状态仍表现为"在运行"；不会把正在跑的审查误报成"已停"。
AC6  已通过（READY）、需返工（REWORK）、需人工（HUMAN_REQUIRED）、覆盖不完整（PARTIAL）等其它状态，
     评论与状态与改动前逐项一致（回归）。
AC7  所有既有自动化测试通过，新增测试覆盖 AC1–AC5，且各含正向、负向与旧会话数据用例。
AC8  真实复测：用 SpinLab #195（目前正停在这个状态）验证修复有效；该复测花钱，不属于代码阶段，
     需用户另行授权，未授权不标记通过。

8. 范围与风险
====================================================================
预计触及：接力判断、会话评论的措辞与覆盖展示、提交状态文字、对应测试与一页说明。
风险：
- R1 把"真实部分覆盖"误当"过期遗留"清掉，导致没审完的文件被当成已审完（最严重，AC3 专测）。
- R2 修了"不挡路"后，接力把本不该继续的会话继续下去，造成额外花费（接力次数与预算上限不变，需测上限）。
- R3 改状态文字/颜色影响现有必需检查或通知逻辑（U3、AC6 回归）。
