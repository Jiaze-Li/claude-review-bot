## 1. 真实问题、受影响的人与失败代价

PR Bot 已先后完成统一审查记录（#97）、入口与模型选择解耦（#98）、删除旧格式导入（#101）、接受 P3 风险（#102）。产品功能趋于完整，但同一业务规则在状态内核、规划、人工结案、自动续审、工作流路由及通知中仍有重复判断或不明确的职责边界。每次增加一种处理方式，容易同时修改多个位置，导致分支之间的状态、提示和持久化记录不一致。

使用者：PR 作者、仓库维护者、ReviewLoop Worker、PR Bot 审查器以及维护 PR Bot 的开发者。
失败代价：未解决问题被误关闭、错误 READY；合法结案反复被重新提出；旧 HEAD 结果误用于新提交；中断恢复失败；重复模型费用；自动接力漏跑或无限重复；不同入口对同一状态得出不同结论；维护成本持续增加。

## 3. 用户可观察的目标

1. Bot 日常仍只需要一个 review 入口；审查范围自动决定，Gemini/Claude 选择只影响提供方，不改变应检查什么。
2. Fix（验证修复）、Dismiss（证伪）、Accept（接受真实 P3 风险）、Override（整个会话人工豁免）保持独立的用户含义，不混淆资格、审查证据、权限或最终效果。
3. 相同输入事实、HEAD 和事件在任一入口只得到一个一致的状态决定；持久化记录、通知、Thread 和 Commit Status 均反映该决定。
4. 每条重要规则有清晰、唯一的负责边界，新增处理方式不再复制整套状态计算、持久化或续审判定。
5. 恢复、去重、预算、审查覆盖和权限保护保持可靠；代码更易维护，而不是仅减少文件或行数。

## 4. 硬性不变量与边界

- **安全**：当前 HEAD 上没有完成必要覆盖/终审，或仍有未解决阻塞问题，不得自动 READY；已有人工 Override 特例必须明确标记且保持原有授权要求。任何数据缺失、被编辑、读取不全、记录冲突、模型不可用或权限不足都不得被当成 PASS。
- **唯一权威**：GitHub PR 中可直接阅读的正式记录仍为持久化审查事实唯一来源；Session 缓存、通知、Summary、Commit Status 只是执行状态或投影，不得偷偷成为第二真相。不得静默丢掉已核实结论、未解决问题或历史授权。
- **产品契约**：保留现有 @gemini / @claude review、Thread resolve、dismiss、accept、override、reset 的输入和语义；Accept 仅现行 `admin` 权限与阻塞 P3，风险匹配与后果说明必需；P0–P2 不通过 Accept 消除。Dismiss 仍必须证据核验。人工 Resolve 不是自动核实。
- **审查链**：首轮、定向修复验证、必要终审、Partial 继续、审查失败恢复和跨 HEAD 判断保持正确；不新增或绕过任何强制审查关卡。
- **预算与执行**：提供方顺序、费用上限、触发权限、并发/锁、幂等回执、相同 HEAD 不重复收费及自动续审限制保持；若需改变任何这些策略，必须作为新的重大决定回到用户。
- **兼容**：现有可恢复的新格式正式记录必须保持可读；#101 明确淘汰的旧格式导入不要求恢复。不得未经用户授权改动历史 PR 评论或迁移正式记录。
- **范围**：允许在原有架构范围内移动、合并、删除无必要的代码和测试；不能只为省行数削弱审查行为，也不能为了重构额外建立并行状态机、数据源或新基础设施。
- **仓库卫生**：正式 main 保留有长期价值且明确归属的项目资产；任务 Plan/Design、临时测试和过程交接不得顺手作为新正式文档长期堆积。保持任务审查证据可通过 PR/不可变提交恢复。

## 5. 明确不做

- 不新增 PR Bot 命令、审查模式或服务商；不重新设计用户交互、风险等级和 Accept 的产品规则。
- 不重新实施 ReviewLoop，不改变 Worker 权限、GitHub App 授权、部署架构、Branch Protection 或自动合并策略。
- 不为了重命名重写历史记录，不重启旧格式兼容，不批量修改已有 PR；若 Design 证明必须更换记录协议，应单列兼容、迁移、回退与用户决策，不得在本任务静默实施。
- 不把每个执行器强行合并为一个文件，不以绝对文件数/代码行数作为验收指标。
- 不做未经明确授权的真实付费模型调用、部署、合并、破坏性操作或权限变更。

## 6. 可观察的全局验收条件

- **AC-01 基线与职责**：Design 必须从本任务真实源码基线建立完整职责/数据流/状态图，列清 `事件 → 决策 → 执行 → 结案 → Ledger → 展示/续审`，对每个共用规则标记唯一负责方与消费者；未审读的模块不得推断为已收敛。
- **AC-02 决策一致**：对新 PR、READY 同/跨 HEAD、REWORK、AUDIT_PENDING、PARTIAL、HUMAN_REQUIRED、REVIEW_IN_PROGRESS、恢复和重复事件建立前后回归矩阵；审查范围、需要人介入的条件、自动续审动作与基线一致，除明确单独批准的缺陷修复。
- **AC-03 结案一致**：Fix、Dismiss、Accept、Override 各自的前置条件、权限、核验、记录、剩余阻塞计算、终审/READY 和后续提示正确；不同业务原因可以区分；不会因复用代码而改变任何结案语义。
- **AC-04 避免重复权威**：状态转换与结案后结果不再由多处各自实现一套相互竞争的业务判断；提供职责清单、关键消费者列表以及相应静态/动态测试证据。重复的只读安全校验可以保留，须解释其边界。
- **AC-05 Ledger 恢复**：清除执行缓存，仅从可信 PR 记录能恢复会话；缺失/修改/折叠/不完整记录、乱序/重复写入、跨 HEAD 与并发场景维持 Fail-Closed；可读的历史新格式记录与新版本行为兼容。
- **AC-06 已接受风险不遮蔽新缺陷**：同一已接受 P3 在原适用条件下保持已结案；等级升级、Failure Path 改变、标题/文件改变、Failure Path 同时缺失等边界都有测试；不能误抑制不同或更严重的缺陷。是否需最小修复按证据在 Design 明示。
- **AC-07 可信用户提示**：审查运行、结案、超时与费用提示不得断言未发生的事实；特别是模型实际被调用时不能声称未使用模型额度。对外文案修正不可改变持久化结果和费用计算。
- **AC-08 资源与权限不变**：预算数额、自动/手动额度差别、模型选择规则、权限、去重、预算预留/结算和线程操作与基线保持一致；测试覆盖条件边界，不重复模型付费。
- **AC-09 完整回归**：现有测试与 CI 全部通过；新增矩阵、恢复、结案和记录完整性测试通过。真实受控 GitHub PR 端到端（包括 Fix/Dismiss/Accept/Override、终审衔接、中断恢复）须单独获得运行与费用授权，未执行则标 `NOT RUN`，不能写成通过；是否为发布阻塞由 Design 在本 Plan 的可靠性要求下明确。
- **AC-10 仓库交付**：最终 PR 只保留必要的产品代码、测试和经明确列出的长期资产；本任务 Plan/Design 不进入 main；汇总设计与实际变更、剩余风险、验证证据和未验收项，不静默扩张范围。

## 7. 依赖、未知与风险

- 已存在的基础：#97 统一 PR Ledger、#98 审查 Scope/Provider 分离、#101 删除旧导入、#102 Accept；其实现位于上述 main SHA，但未将合并记录当作在线验证。

- 设计阶段需提供至少两条收敛路线的 Options、明确 Assumptions、正式资产清单、回滚路径、验证门槛与末尾 Work Contract；不要预设必须重写 Ledger。
