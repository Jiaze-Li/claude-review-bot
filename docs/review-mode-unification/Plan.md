## 1. 真实问题

当前 PR bot 存在“深度审查（Deep Review）”“完整审查（Full Review）”“普通审查”“增量审查（Incremental）”“修复验证（Verification）”等容易混淆的名称和入口。其中有些表达**审查范围**，有些表达**模型提供方**，还有些表达**运行方式**。

实际实现中，全量审查可能内部走名为 `claude` 的执行模式，但该模式默认仍是 Gemini 优先、Claude 后备；`@claude review` 则只是指定 Claude 作为模型，并非额外或更高级的一轮审查。用户难以判断是否需要主动挑选“深度审查”，维护者也容易把模型选择、审查强度、阶段调度和预算策略耦合到同一分支逻辑，继续积累补丁。

本任务要解决的是**概念和职责混用**，不是证明某个模型更好，亦不是重新构建新的审查引擎。

## 2. 使用者与失败代价

- **使用者**：PR 作者、项目维护者、本地 Coding Worker、PR bot。
- **日常失败代价**：需要学习多个看似不同的 review 入口；误以为换模型就能获得更深的审查；人为选择不充分的审查范围。
- **工程失败代价**：新增功能时重复编写条件判断；在模型回退、全量审查、修复验证和最终 READY 之间出现不一致；改名或重构时破坏既有审查结果、模型预算或恢复能力。

## 3. 确认的产品需求

### 3.1 一个日常审查入口

日常 PR 审查继续采用一个主入口（当前为 `@gemini review`）。使用者不需手动选择 Full、Deep、Verification、Incremental 或 Final Audit。

Bot 应根据**当前 PR 的正式审查记录、最新 HEAD、工作流所处阶段、新代码影响以及已有审查覆盖证据**，自动决定执行足够范围的审查。用户只需要知道正常的提交与复审操作。

首轮审查、问题验证、自动衔接的终审、终审后的必要收尾，以及例外升级检查的整体流程，沿用 PR #97 已冻结的标准工作流，不创建新的日常阶段。

### 3.2 审查范围有清楚、统一的语义

从用户的角度只需要理解两种实际工作：

1. **完整审查**：覆盖当前 PR 需要审查的完整改动及必要上下文。用于首轮全量、终审，以及此前审查证据不足以覆盖高影响新提交等情况。
2. **针对性审查**：在已有有效审查证据基础上，核对未解决问题和新增代码差异及相关回归风险。用于修复验证、以及已 READY 后的小范围安全增量等场景。

这两种描述的是**检查范围**，不是不同的模型等级、用户命令或相互独立的质量标准。现有 Verification、Incremental 等内部任务可以保留必需的差异化输入/输出语义，但用户不应被迫选择它们。

审查范围不足、证据过期、提交影响超出既有结论或范围无法安全确定时，必须扩大检查或安全阻塞；不能因为“针对性”比较省钱就自动放行。

### 3.3 模型选择独立于审查范围

- 默认仍采用当前可用的 Gemini 优先、Claude 后备策略；模型提供方是执行选择，不是审查生命周期或审查强度。
- `@claude review` 如继续保留，应明确属于**人工指定模型的高级入口**，不改变原本应做的 Full / Targeted / Audit 等检查范围，不自动增加或减少必需的审查关卡。
- 用户没有选择模型时，系统自行依据已存在的配置、可用性、预算及安全限制调用模型；不能把后备切换宣传成“更深一层审查”。
- 模型失败、额度耗尽、工具能力不足或审查覆盖未完成时，仍需如实记录、继续合法后备路径或停止；不得把某个模型返回“无问题”当作覆盖完整的证据。

### 3.4 “深度审查”不再作为独立的产品工作流概念

对外说明不再把 Deep Review 当作与 Full Review 并列的另一套审查流程。内部模块名称是否重命名、如何处理历史参数、是否复用现有分片执行器，属于 Design 的路线选择；不得为统一术语而无必要地重写成熟的审查执行能力。

在审查报告中可以保留真实的执行细节（例如分片、使用模型、覆盖范围），但必须明确它们不代表额外的审查阶段。

## 4. 硬性边界约束

- **不改变 PR #97 冻结的产品合同**：GitHub PR 是正式审查记录来源、Thread 问题处理、自然语言 dismiss、问题级修复历史/状态、审查循环及终审收尾等职责保持不变。
- **不改变 READY 的真实性门槛**：当前 HEAD、完整覆盖、未解决问题、终审、回归检查和不确定项仍由既有正式证据约束。指定 Claude 不构成直接放行。
- **不跳过高影响改动的扩大审查**：修改共享状态、事务/权限边界或审查基线发生实质变化时，应进行足够范围的检查。
- **不因概念统一取消必需的工程安全**：权限、认证、固定 HEAD、并发互斥、幂等、预算/计费、模型隔离、故障恢复、分片与部分覆盖 fail-closed 均需保留。
- **同一审查工作流，只允许一处权威范围决策**；其他执行、发布和模型适配逻辑应服从决定，不再通过同名词的特殊分支重新判定审查阶段。
- **不能把静态源码判断当作线上验收**：设计及测试必须区分本地证据、CI 与真实 GitHub PR 运行证据。
- 当前 PR #97 尚未合并到 `main`，本任务后续 Design/Code 必须核实 #97 的实际最新 HEAD、验收/集成状态与最终代码基线；未经明确授权，不替 #97 合并、发布或更改其冻结合同。

## 5. 不做什么

- 不新建“深度审查”的另一个付费或独立质量关卡。
- 不重新设计审查状态界面、PR 评论外观、历史记录持久化或自然语言 dismiss。
- 不重新实现 Gemini / Claude 客户端、分片执行引擎或 ReviewLoop。
- 不把所有审查强制设为全量，也不把所有审查强制设为增量。
- 不删除已证明必要的模型后备、人工指定模型及异常恢复入口。
- 不因精简名称而默默改变模型费用授权或现有预算上限。
- 不在本次 Plan PR 内修改功能代码、部署服务、修改权限或合并任何 PR。

## 6. 可观察的验收条件

1. **日常入口一致**：用户通过 `@gemini review` 即可进入正确审查环节，无需判断 Deep、Full、Verification 或 Incremental。
2. **首轮完整检查**：对一个新 PR（或此前没有有效审查证据的 PR）执行完整审查；无阻塞且覆盖完整时可以 READY。
3. **修复验证**：在有未结案问题的 PR 上，新增修复提交后统一核验原问题、差异及其相关回归，不因模型选择而省略必要检查。
4. **终审/收尾**：首轮问题结案后按 PR #97 的合同进入全量终审；终审问题修复后审查范围充足才 READY。
5. **大改动升级**：原先完成审查的 PR 发生较大或关键边界变动时，不能无条件沿用旧 READY 或用过窄的增量检查放行。
6. **提供方解耦**：同一 PR、同一事实状态下，默认 Gemini-first 和显式 Claude-only 请求的**必要审查范围和 READY 判定规则一致**，差异仅为模型策略及相应费用/可用性。
7. **分片与部分完成**：大 PR 分片、运行超时、预算不足时，未审文件或不确定事项被明确记录且仍阻塞；后续恢复不重复计入已完成覆盖。
8. **不重复工作**：相同 HEAD 上重复触发普通审查不无谓重跑；各级重试与后备不重复结案、重复收费或覆盖有效审查事实。
9. **记录可理解**：人类可见报告能分清“本轮检查了什么、是否完整、是否需要我操作”；默认折叠详情可追溯模型、范围、提交和证据；不再用“Deep”暗示额外审查等级。
10. **兼容与回归**：既有命令、旧正式记录和必要审核配置的迁移/兼容经过验证；出现不兼容或不可确定时安全停止而不是清空记录。
11. **集成验证**：自动化测试覆盖上述正常与失败路径；至少一次真实 GitHub PR 的端到端验证明确区分已执行、未执行和失败的证据。没有证据不能声称 PASS。

## 7. 已确认决定、仍未知的前提

### 已确认的决定

- 不再对外保留“Deep Review vs 普通 Review”这种独立审查等级。
- 统一日常审查入口，由 Bot 决定完整检查或针对性检查。
- 审查范围与模型选择是两个不同维度；人工指定 Claude 不改变必需审查范围。
- 保留必要的针对性验证、全量审查、模型后备和安全保护。
- 不修改 #97 的冻结需求；本任务独立于 #97，实际实施依赖其代码与集成状态。

### Design 阶段需要核实（不是新的产品决策）

- #97 的最终代码何时真正进入被实施的基线，以及此时是否有未完成的独立审查/线上验收。
- 当前各执行入口、调度模块、命名和模式参数中哪些职责重复，哪些仅是历史兼容别名。
- 全量和针对性检查的共同逻辑边界、所需不同输入/结果协议及覆盖判据。
- 指定提供方、后备/额度、历史参数和现有工作流配置的兼容性。
- 审查记录、线程核验、提交检查及 PR 状态的真实端到端行为。

具体代码组织和改名范围由 Design 比较 Options、声明 Assumptions 并在 Work Contract 中固定；不可直接把上述候选实现写成已授权变更。
